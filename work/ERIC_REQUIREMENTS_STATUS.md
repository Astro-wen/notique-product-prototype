# Eric 要求与当前真实状态

更新日期：2026 年 8 月 12 日

## 先说结论

核心链路已经在本地真实跑通。系统可以接收一次或多次沟通材料，提取带原文证据的项目记录，让人确认、拒绝、修改和补关系，再用确认后的记录生成项目现状、时间线、决定、偏好变化、待确认问题、风险、下次沟通清单和会前速览。音频上传、说话人转写和后续分析也已经跑通。

Eric 的 Concept Validation 目前没有通过。主要问题很明确：重要事实召回不稳定，跨会议关系会漂移，图片事实几乎没有被独立提取，Brief Card 没有达到规定格式和可用性，真人两分钟审核还没有测试。完整应用已经可以从 GitHub Pages 跳转到公开的 ChatGPT Sites 使用。界面、录音、转写、双阶段分析和分段计时都已经进入线上测试版本。

因此，当前成果可以称为可继续测试的工程原型。它已经证明核心架构能工作，也准确暴露了模型质量和公开部署的问题。现在还不能对外说产品概念已经验证。

这轮先按 Eric 的 MVP 收口。核心范围是三类 Transcript 案例、带证据的 Claim、人工审核、已确认项目记忆、跨沟通变化和项目结果。音频入口作为已经完成的扩展保留。公开多用户部署、第二位标注者、Blind Eval、复杂运维和多段录音管理不阻塞这次 MVP。Prompt v7 的三行业真实运行已经完成；剩下必须取得的核心证据是模型质量改进后的同输入稳定性，以及一次不看 Ground Truth 的两分钟真人审核。

## 这次方案如何回应“不靠 Verification”

这句话不应理解为取消人工核对。Eric 真正想知道的是：人工开始修正以前，AI 第一版本身是否已经有用。如果最后只有人工改完的报告是正确的，我们就无法判断 AI 是在节省工作，还是把整理工作换了一个界面让人重新做一遍。

方案现在把这两个结果分开：

1. **AI 第一版是否有用。** 分析完成后先显示整场初稿。用户可以记录“基本可用”，也可以指出 AI 漏项。这个评价不改变任何事实状态。
2. **人工核对后的正式结果是否可靠。** 用户随后逐条看 Evidence，确认、修改、拒绝并处理 Relation。只有这一步完成的内容才进入 Verified Ledger 和报告。

因此，Verification 仍然是安全门，但不再被用来掩盖 AI 第一版的质量。系统会保留 AI 初稿、人工补充、修改、拒绝和关系决定的数量，让 Eric 能看到 AI 到底节省了多少工作。

目前已经完成这套记录和交互；还没有完成的，是让非开发者用真实材料走一次并得出“初稿可用率、漏项数、修改量和审核时间”。这组数据才是下一步判断方案是否真的有效的依据。

## 三类要求需要分开看

### 1. Eric 的长期产品方向

Eric 的产品 Concept 关注的是专业人士长期使用的项目记录。每次沟通产生的重要事实都要带原始证据，由人确认后进入项目记忆。后续沟通继续使用已经确认的内容，只补充新情况、变化和未解决问题。最终输出包括项目时间线、决定记录、客户偏好变化、待确认问题、矛盾与风险，以及会前可以快速查看的 Brief Card。

这部分定义了长期产品方向。它还要求系统保留人的判断权。模型没有把握时应提出候选和追问，用户可以核对证据、纠正内容和修改项目关系。

### 2. Eric 的两周 Homework

两周 Homework 把范围收得很小。输入是一到十份已经带时间点的 Transcript。用户点击一次后，系统生成 Claim Ledger 和结果页。每条 Claim 要能回到原文。用户确认、拒绝或修改后，结果页必须马上变化。下一次分析只能继承已经确认的内容。

Homework 要求准备 Contractor、Realtor 和 Insurance 三个场景，每个场景有三到五次沟通。正式质量门包括重要事实召回至少 80%，原文引用准确率 100%，时间点误差小于 5 秒，同一输入重复运行稳定，审核时间少于 2 分钟，以及 Brief Card 固定包含一个现状、两个变化、两个问题和一个风险。

Homework 明确把 UI、录音和语音转写放在核心范围之外，默认输入 Transcript 已经准确。现有最小界面只是为了让真实测试可以完成。

### 3. 后来增加的图片和音频入口

为了更接近真实产品，后续又加入了图片和录音。图片会和 Transcript 一起进入模型。录音会先保存，再生成带说话人和时间点的 Transcript，然后进入同一套 Claim、审核和结果页流程。

这两项值得继续做，但验收要单独记录。音频链路跑通不能代替 Transcript 抽取质量验收，图片能上传也不能说明图片理解已经达标。

15. 核心测试页已经加入分段计时。一次分析会分别显示排队、准备材料和项目上下文、第一轮识别事实、第二轮查漏纠错、必要的加强复核、验证与保存，以及等待人工核对的时间；录音转写和报告读取也各自显示耗时。计时读取服务器已经保存的开始与结束时间，刷新页面不会把已经完成的模型阶段重新计时。
16. 核心流程已经改成引导式工作流。材料准备后，页面只突出当前真正需要做的一步。分析结束会自动进入使用场景确认或第一条审核，不再要求用户自己寻找标签页。
17. 审核已经改成连续模式。桌面端同时显示待核对队列、原始证据和当前决定；手机端一次聚焦一条。确认、修改或不采纳后会自动打开下一条，Relation 仍必须逐条接受或拒绝，Evidence 不完整时仍不能确认。
18. 本次沟通审核清空后，系统会自动选择下一次沟通，但不会自动开始下一次付费分析。用户再点击一次，才会产生下一次模型请求。全部沟通完成后会自动打开会前速览。
19. 页面会记住最近打开的 Project 和 Event，并在刷新后从服务器恢复真实任务阶段。浏览器只保存 ID 和导航意图，不保存业务材料、Claim、Verdict 或报告。
20. 沟通列表和当前沟通现在只显示一个统一状态，例如“正在转写”“正在识别事实”“等待人工核对”或“需要处理”。后台等待超过页面时限时显示“仍在后台运行”；重新检查不会创建第二个 Run。
21. 分析完成后，页面会先显示整场 AI 初稿，而不是立刻把用户丢进第一条 Claim。初稿按决定和要求、金额和日期、偏好和材料、问题和风险等主题分组。用户先判断 AI 是否理解大意，再开始逐条核对。
22. “这份初稿基本可用”只记录对 AI 第一版的评价，不会确认任何事实。这个设计直接避免把 Verification 变成掩盖模型质量的手段：我们可以分别看 AI 第一版是否有用，以及人工修正后正式结果是否可靠。
23. 用户发现 AI 漏项时，可以在当前沟通的完整 Transcript 中选择原文并补一条待核对记录。人工补充同样要经过确认和 Evidence 门槛，不能直接进入报告。
24. 审核顺序会把金额、日期、决定、责任人、需要补证据的内容、候选关系和人工补充放在前面。短引文可以展开前后相邻原文，降低断章取义的风险。
25. 本次审核结束后，页面会把 AI 初稿数量与最终确认、修改、拒绝、人工补充和关系决定放在一起显示。这个对比是确定性统计，不调用另一个模型包装结果。

这些项目说明确定性的工程底座已经能支撑真实评测。它们不代表模型质量已经通过。

## 这次体验调整解决了什么

原来的工程功能大多已经存在，但使用时像在多个工具页之间来回跳。用户要自己记住当前 Project、当前沟通、Run 是否完成，以及审核后该回到哪里。这个问题不会直接降低模型准确率，却会让第一次使用的人误以为流程卡住，甚至重复点击分析。

现在方案把同一套后端能力连成一条清楚的路：添加材料，开始分析，确认场景，连续核对，继续下一次沟通，最后查看会前速览。系统负责导航，人仍负责事实和关系判断。这个边界很重要，因为自动跳转可以减少无意义点击，自动确认却会破坏 Eric 要求的 Human-in-the-loop。

这次调整不能解决模型漏掉事实、错误判断前后关系或图片理解不足。它也不会让 Luna xhigh 本身变快。它解决的是“下一步在哪里”“刷新后会不会丢”“是不是又付费了”“为什么审核完还停在空页面”这些产品摩擦。准确率仍要按后面的固定样本和硬门继续提升。

## 这次速度优化如何理解

“识别事实”变慢不一定只有一个原因。它可能慢在后台排队、把多张照片和已确认项目记录整理成上下文、第一轮 xhigh 深度盘点、第二轮 high 查漏，或者模型完成后验证并保存结果。过去页面只显示一句“正在识别事实”，所以很难判断应该优化哪里。

这次先做两项不会降低准确率的调整：

1. 多张照片、项目已确认记录和词汇表改为同时准备，避免图片越多，准备阶段就按张数逐个等待。
2. 两个模型阶段把相同的长材料放在稳定的共同开头，并使用同一次运行的缓存标识。第二轮仍会看完整材料，但有机会复用第一轮已经读取的部分。第一轮仍是 xhigh，第二轮仍是 high，Evidence 和人工审核门槛没有放松。

下一次真实测试需要记录每个阶段的时间和缓存命中。若大部分时间确实花在第一轮 xhigh，下一步应拿同一份材料比较 xhigh 与 high 的 Recall 和延迟，再决定是否提供“快速测试”和“高质量验证”两档；在数据证明质量不下降以前，方案不会直接降低推理强度。若时间主要花在加强复核，方案应先修复触发规则和 Prompt，让正确结果少走第三轮。若时间主要花在排队或准备材料，则继续优化调度与文件读取，而不是改模型质量。

### 2026 年 8 月 12 日的 30 分钟卡住问题

这次现场测试给出了很清楚的答案。页面显示排队只用了 619 毫秒，准备材料和项目上下文用了 664 毫秒，剩余三十多分钟全部停在第一轮“识别事实”。运行记录里没有 Provider Request ID，也没有输入或输出 Token，说明这不是模型正常思考了三十分钟，而是一次请求失去响应后，后台没有及时把它收回。

检查同时发现，线上生产环境误用了 `max`。这与当前方案不一致。方案已经统一为：第一轮只使用 `gpt-5.6-luna + xhigh`，第二轮只使用同一个模型的 `high`，必要的加强复核再使用 `xhigh`。代码不再接受 `max`；即使环境变量以后再次误填，也会安全回到 `xhigh` 或 `high`。

恢复规则也随之收紧。模型阶段连续十分钟没有完成记录时，系统会主动检查任务。冻结为 `xhigh/high` 的任务可以在同一个 Run 和同一个幂等请求下恢复，避免重复创建任务；冻结为旧 `max` 的任务会安全结束，不会继续消耗时间，用户重新分析时才会建立新的 `xhigh/high` Run。这个修复解决的是“请求失去执行者后一直显示处理中”，不代表所有 xhigh 分析都能在十分钟内完成；正常延迟仍要用下一次真实 Run 的阶段计时验证。

修复发布后，方案在同一个 Project 和同一批 80 段 Transcript 上立即重新测试。新 Run `run_258eea7b5d0343d88f165a40766aa4df` 使用 `gpt-5.6-luna`、Prompt v8.2 和 Schema v3，在 2 分 20 秒内完成。第一轮 `xhigh` 用时 95.1 秒，第二轮 `high` 用时 43.0 秒，验证与保存用了 0.4 秒；排队约 1 秒，材料准备约 0.6 秒。两轮合计使用 34,240 input tokens 和 21,066 output tokens，这次没有缓存命中。

这次 Run 最终留下 4 条待人工核对记录，并以“完成，有部分提醒”结束。程序拒绝了 6 条无法和服务器原文完全对齐的候选，没有把它们写进审核队列。这说明新的速度和恢复路径已经正常，也说明证据安全门在工作；它不能被解释成准确率已经通过。下一步应确认这些被拒候选是模型引用方式不够精确，还是转写分段和中英文混合造成匹配困难，再决定优化 Prompt 还是证据匹配规则。

## 音频上传与转写

音频是后续增加的产品入口。它已经通过正式代码链路完成一次端到端验证。

测试输入是一段 14.559 秒的双说话人合成 WAV。音频保存到 R2 后，`gpt-4o-transcribe-diarize` 在约 5.8 秒内生成 3 段带说话人和毫秒时间点的 Transcript。Transcription Run ID 为 `trun_95fddbdb48c14f7abcaf8117a6f781e0`。

派生 Transcript 随后进入正式 Extraction。Run `run_9e2a97559e644b2eb5b4ad9442c79db1` 使用 `gpt-5.6-luna`、`reasoning=max` 和 Prompt v5，生成 5 条候选。五条都经人工核对后进入 Verified Ledger，项目结果页和音频时间点播放正常。

这项结果可以标记为工程闭环完成。最小测试界面也已经补齐 audio-first 使用路径。空白状态可以先建立 Project 和第一次沟通，再直接上传录音。转写或分析失败后，录音不会丢失，用户可以重新转写、重新分析或继续检查后台状态。轮询超时会显示可恢复操作，完整逐字稿可以按说话人和时间点查看。

最新一轮还补齐了转写任务的恢复边界。网络超时、429 和服务端临时错误会在同一个 Run 内有限重试。Provider 已经返回并写入暂存区后，即使数据库写入失败，后续重试也会复用暂存结果，不会再次调用 Provider。旧 Run 不能覆盖新 Run 的录音状态，进入 dead letter 时 Run 和录音会在同一事务中变为失败。录音文件支持按字节范围读取，所以浏览器可以从指定时间点开始播放，不必重新下载整段文件。

2026 年 8 月 12 日用一段 4 分 12 秒的真实 M4A 做使用测试时，文件上传和模型调用都成功，但整块转写结果没有通过完整性校验。系统随后改成逐段接收模型返回，减少长逐字稿在末尾被截断的风险；多人抢话造成的片段乱序会按原时间点重新排列。若模型没有发出完整结束标记，系统仍会拒绝写入半份逐字稿。失败页面现在会直接显示具体原因，便于判断应该重试还是调整录音。

仍有一个无法靠本地代码完全消除的边界。如果 Provider 已经收到并计费，但网络在响应回到本服务前断开，本服务无法知道对方是否完成。当前使用同一 Run 的稳定幂等键降低重复调用风险。最终是否能完全避免重复计费，还取决于音频 Provider 是否保证该请求头的幂等语义。

现场噪音、远场、多人口音、抢话、不同收音设备和转写错误率都没有测试。Eric Concept 中与真实收音质量有关的判断仍然未验证。

## GitHub Pages 和完整应用的当前关系

旧截图中的 `Request failed (405)` 来自当时的公开 GitHub Pages。GitHub Pages 只能托管静态文件，无法运行 Next.js API Route、数据库、R2、后台转写和模型调用。页面向同一地址发送上传或分析请求时，没有后端可以接收 POST，所以返回 405。

这个旧部署问题已经处理。GitHub Pages 现在只显示一个很轻的入口，并把用户带到 Sites 上的完整应用，因此不会再从静态页面直接发送上传和分析请求。完整测试地址是 `https://notique-evidence-workspace.uclae2e12.chatgpt.site/`。

目前的 Sites 适合 Eric 按说明测试一套共享的 MVP 数据。它还不是正式的多用户 SaaS：测试者会进入同一个测试 Workspace，共用项目数据和模型额度。方案没有把这个长期权限问题包装成已经完成，因为它不属于本轮 Eric Homework 的核心验证，但正式给不同客户使用前必须补上 Workspace 隔离和费用边界。
