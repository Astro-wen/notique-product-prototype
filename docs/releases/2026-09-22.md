# 2026-09-22：第一次用真实音档跑通全链路

一份 32.5 MB、14 分 09 秒的真实房产买方沟通录音，从上传到五个阅读视图和
24 条待确认事实全部出来。之前从没成功过，不是某一处坏了，是链路上五处
各自坏着，前一处修好下一处才露出来。按发现顺序记下，每一处都有提交。

## 1. 传不进来：音频上限守错了东西（f19fb7a）

报「超过 25.0 MB 的单文件上限」。25 MB 是 OpenAI 的单文件限制，但转写那
一侧根本看不到原件：浏览器先按三分钟切块，块是 16kHz 单声道 WAV 约
5.5 MB，原件上传后只做存档。代码常量本来就是 100 MB，.env.example 也是，
是本地 .env.local 被手工调成了 25 MB，而服务端取 min(环境变量, 常量)，
只能往低调。对齐样例配置，常量处写明它不是转写服务的限制，两条测试钉住
「块远小于上限」和「样例配置等于常量」。线上托管环境的同名变量要单独核对。

## 2. 开发模式弹报错框：两个 ResizeObserver 在回调里改样式（2b1e842）

良性告警，但 vinext 把它当致命错误盖住整页。SmoothResize 和阅读区高度两处
都在观察回调里同步写影响布局的样式，浏览器同一帧反复回到回调。推到下一帧
并按帧合并，逐帧验证动画未变，只是晚一帧开始。

## 3. 五个阅读视图全灭：产物指纹三处算得不一样（3ca6c72）

十个运行记录无一例外 ARTIFACT_INPUT_HASH_CHANGED。这是上一轮改内容寻址时
漏掉的：创建那一处按新定义去掉了 extraction_run_id，领取时校验的那一处和
重试那一处还带着它，创建出来的指纹和校验算出来的永远对不上。重试那一处
还把四个阅读视图的契约版本写成易读稿的。三处对齐，测试钉住字段集合并禁止
extraction_run_id 回来。

## 4. 重新生成点不通：路由只认两种，按钮传的是旧种类（4e8b334）

指纹修好后视图还是出不来，因为「生成阅读总结」这条路本身断在两层：路由
的 ARTIFACT_KINDS 手写成 summary 和 readable_transcript，四个阅读视图的
重试请求直接 400；界面按钮传的是不再生产的 summary。路由改成从
READING_ARTIFACT_DEFINITIONS 派生，按钮只重试失败的种类、按脊椎顺序提交、
派发器叫一次。单种类重试路径没有调用方了，连同六处 prop 一起删。

## 5. 成功了却不显示，概要抄坏一个 id 就整份作废（4ea2b21）

章节、发言总结、要点回顾在库里成功，界面退回兜底：前端 sourceSegmentIds
只认 summary 和 segments 两种形状，四个视图算出零引用，被当成不属于当前
原文过滤掉。改成收进所有已知集合。概要六次重试全是模型把 40 字符的段落
id 抄坏尾巴（..._00104タ）。加一条窄修复：去掉尾部非 [A-Za-z0-9_] 字符后
必须正好命中一条真实段落才修，否则照旧报错。修出的引用一定指向真原文。

# 同日第二批：第二次真实音档跑出来的三处

用户按 5 处修复后的版本重新上传同一份录音，章节仍失败、整体仍慢。
根因和上一批不同，记在这里。

## 6. 等待被记成失败次数（58a2547）

leaseRun 每领取一次就把 attempt_no 加一，而下游视图等上游、易读稿等下一
批分块时被领起来又放回，都不是失败却都算了一次。等易读稿那几分钟里下游
被领十来次，attempt_no 到 25，早过上限 3。之后模型第一次抄错 id，
retryInvalidOutput 一看次数已耗尽直接判死，界面上就是「这次总结未完成」。
放回时对称地减一，attempt_no 只数真正打到模型的次数。

## 7. 章节白等易读稿（58a2547）

章节声明依赖易读稿，但 provider 给章节喂的一直是原始分段，
readingUpstreamContent 也不认易读稿。这个依赖只是让章节干等三万多 token
生成完。去掉，章节和易读稿同一波并行。事实识别同样不用易读稿，本地已把
AI_READABLE_TRANSCRIPT 关掉，阅读线的关键路径变成
章节 → 发言总结/要点 → 概要，三跳。

## 8. 后台响应在供应商侧卡住没有预算（88a6f16）

易读稿第 4 块在 OpenAI 那边 in_progress 十二分钟没吐一个字，同批另外三块
一分钟就完。代码只会每五秒 GET 一次直到三十分钟的任务上限。恢复路径上按
响应的 created_at 算年龄，超过预算就 POST cancel、丢掉 id、下次重新 POST；
抽取阶段把这次尝试标 failed 后自然开新 attempt。阅读产物预算五分钟，抽取
阶段用自己的超时。那一块最终在 20 分钟后自己完成了，发生在这条上线之前，
所以线上没触发过，只有单元测试覆盖。

## 阅读区加了五步进度

每种只看最新一次运行，完成后收起。模型调用没有中间进度，能诚实报的是
到第几步。

## 验证

622 项单元测试、TypeScript、ESLint 全过；桌面 Playwright 全量两次，一次
78 过 2 败（两条单独重跑都过，是首帧可见性竞态），一次 80 过 0 败。

# 同日第三批：阅读线从三跳并成两跳

## 9. 发言总结和要点回顾不再等章节

它们本来就声明「章节没出来就退回整篇读」，所以章节对它们不是硬依赖，
只是有了更省事的目录。之前把章节写成 dependsOn，等于让两个能立刻开工
的 agent 白等一分多钟。现在 reading-pipeline 里多了 optionalUpstream：
派发时不等，取上游时有就带上。阅读线关键路径变成
章节 / 发言总结 / 要点回顾 同一波 → 概要，两跳。

说明页的图和文字改成同一排三个并行、概要在下、易读稿另起一路默认关。

## 计时

同一份 14 分钟录音，转写好的逐字稿上重跑（本地，Luna）：

| 步骤 | 改前 | 改后 |
| --- | --- | --- |
| 发言总结 | 等章节出来再跑 | 与章节同时开工，28 秒 |
| 要点回顾 | 同上 | 29 秒 |
| 章节 | 34 秒 | 第一次输出无效重来，共 2 分钟 |
| 概要 | 章节和另两样都完才跑 | 20 秒 |
| 阅读线合计 | 2.5 分钟 | 顺利时约 1.5 分钟 |

阅读线本来就不是大头。同一录音事实线三次实测 6.5、8.1、9.7 分钟，
全程等于转写 1.4 分钟加事实线。事实线三段里：清点 xhigh 2.5 到 3.9 分钟，
核对 high 1.8 到 5.1 分钟，重核每次都被 compound_claim 触发再加 1.8 到
2.3 分钟，三次里有一次重核输出无效白跑。把清点降到 high 实测一次：
清点 1.7、核对 1.7、重核 2.3，合计 5.8 分钟。要再砍一半，得动重核的触发
条件或把核对也降档，这两处都动结论质量，留给本人定。本地 .env.local 的
AI_REASONING_EFFORT 已按实验改成 high，线上没动。
