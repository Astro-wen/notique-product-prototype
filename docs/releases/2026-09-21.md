# 2026-09-21 release validation

This release rewrites the workspace copy in the user's own words, makes the
sidebar behave the same on every screen, stops the project card's hover action
from covering the date, compresses the workspace top bar, and replaces the
materials import panel with a single drop zone that supports reordering and
renaming.

## Copy

`沟通` is now `记录` throughout the interface — 126 replacements across the
workspace, project index, navigation labels, export filenames and view copy.
Mechanism descriptions no longer appear on screen; they live in code comments,
so the interface says what the user gets and the source says how it works.

## Interface

- The workspace no longer forces the sidebar into a 68px icon rail, and no
  longer hides the collapse button. Sidebar width follows the user's own
  preference on every screen, so walking from project management into a
  workspace does not reshape it.
- The project card's hover action was absolutely positioned over the card's
  date and covered it with a white background. It now occupies its own row;
  card height is unchanged.
- The project/record bar went from 92px to 65px. The labels sit beside their
  selects instead of above them, and the selects are sized to their content.
  Content starts 27px higher.
- Materials arrive through one drop zone that accepts recordings, transcripts
  and images together, replacing the four separate import buttons. Materials
  can be dragged into any order or moved with the arrow keys, and renamed in
  place. A reorder that fails on the server rolls back to the stored order.

- Copy: 126 machine-toned strings rewritten in the user's own words. Sentences

- Phone: the demo notice no longer sits on top of the project bar (a `top`

## Extraction reliability (third batch)

Production failed two extraction runs in a row with `MODEL_OUTPUT_INVALID`.
Reading the persisted `error_details` showed the model was not getting the
content wrong; it was filling the form wrong: a duplicate `inventory_key` in
`candidate_dispositions`, a missing disposition for one candidate, and a claim
carrying a structured uncertainty while leaving `needs_additional_evidence`
false. Three changes follow from that.

- A failed escalation no longer discards a verification that already
  succeeded. The fallback (warn and keep the base verify) existed only on the
  path that starts escalation inside the current invocation. The path that
  resumes an in-flight escalation had no `try`/`catch`, and with background
  responses that is the common path: an HTTP invocation keeps `waitUntil` work
  alive for about 30 seconds, so a three-minute escalation is almost always
  resumed rather than completed in place. Run `...35a802fc` failed that way
  with a succeeded `verify` stage on record.
- Two contract violations are now repaired instead of rejected. A duplicate
  disposition keeps its first occurrence; a structured uncertainty forces
  `needs_additional_evidence` to true, which is the cautious direction because
  it only sends the claim to human review. Every repair is reported in the
  validation result so it can be recorded rather than silently applied.
- A missing disposition is no longer a contract failure. It is already a
  semantic signal downstream: `assessVerificationEscalation` counts it as
  `inventory_candidate_unmapped`, and a critical candidate also lands in
  `droppedCriticalInventoryKeys`. Failing at the validator meant the same
  condition was handled twice and the escalation path never saw it, so the run
  was re-run instead of re-verified. This now matches how an explicit drop
  already behaved.
- Escalation still runs at the base verifier effort. The stronger notch is
  computed and frozen into the run's model params at creation, so raising it
  later is a one-line change that keeps the frozen profile honest about cost,
  but it is not switched on: there is no measurement yet showing a higher
  effort fixes these contract violations, and the deterministic repairs above
  already cover every failure mode observed in production.

Production is configured with `AI_REASONING_EFFORT=low` and
`AI_VERIFIER_REASONING_EFFORT=low`, not the `xhigh`/`high` in the local
environment file. That is a hosting variable, outside this release.

## Reading pipeline restructure (fourth batch)

The four reading views were four required fields of one model call, so a single
contract violation lost all four; production lost them that way. They were also
re-produced on every extraction retry, because an artifact run's identity was
the extraction run that happened to create it. Three runs over one unchanged
transcript re-paid for a summary that had already succeeded and for a readable
transcript whose output is 52k to 71k tokens.

- Artifact runs are content-addressed. The idempotency key is now the hash of
  the input manifest, model, effort, prompt and schema, so retrying an
  extraction reuses everything that already succeeded. Material or prompt
  changes still produce a new key and a fresh run.
- The four views are separate artifact kinds with separate runs, contracts and
  retry budgets: `chapters`, `speakers`, `key_points`, `overview`. The old
  four-in-one `summary` kind is no longer produced; existing artifacts remain
  readable and act as the reader's fallback source per field.
- Chapters are the spine. `lib/domain/reading-pipeline.ts` declares the graph
  and the readiness rule: a downstream view waits while its upstream is queued
  or processing, runs degraded when the upstream terminally failed but it can
  still read the transcript itself, and is abandoned without spending a call
  when it cannot work without the upstream at all.
- The overview never reads the transcript. It is written from the chapters,
  speaker summaries and key points, citing the segment ids those entries
  already carry. That is why splitting one 88k-token call into four does not
  cost four times as much.
- Every per-view result is wrapped back into the original envelope shape and
  validated by the existing validator, so citation existence, single-asset
  scope, transcript ordering and speaker consistency are all still enforced,
  with no second validation path to keep in step.

Prompt caching is requested correctly (the 110k shared context leads the
prompt, the stage instructions follow, and the cache key is stable within a
run) yet production reports zero cached tokens on every stage. The cause is on
the provider side and needs one paid experiment to pin down. The restructure
above does not depend on it.

## Material routing, end to end (sixth batch)

Dropping material on the home page always created a new project, and there was
no way to move a record afterwards, so material that belonged with an existing
client had to be filed by hand or not at all. Three layers now exist.

- **The picker.** Dropping on the home page asks once which project the material
  belongs to, listing recent projects plus 新建项目. Skipping means what it meant
  before, a new project. One batch is asked once, not once per file: a batch
  uploads serially and `project` does not update inside that closure, so the
  answer is held in a ref. Returning home forgets it. With no projects to choose
  from the picker does not appear at all.
- **The answer is recorded.** `events.routing_source` stores `user` or `skipped`.
  It exists so the suggestion layer can stay silent about material the user
  already placed deliberately; re-uploading never overwrites the first answer
  (`AND routing_source IS NULL` on the update).
- **The suggestion.** After `overview` completes, Jev is asked once which
  existing project the material resembles, or none. Above 0.8 a bar appears on
  the record; below it nothing happens. The bar never states the probability:
  a bare 0.87 invites the reader to guess what the number means, and the number
  is kept for evaluation, not for the reader. Accepting moves the record.
  The whole layer sits behind `PROJECT_ROUTING_ENABLED`, off by default.
- **Moving a record** rewrites `project_id` across the ten child tables that
  carry it, appends a fresh `sequence_no` in the destination, and deletes the
  suggestion. It is refused while anything human-reviewed depends on the record:
  verdicts, claim relations, review attestations, occurrence links, cross-event
  references, an active review session on either project, or the record being
  `sequence_no = 1` of a source project whose scenario is still unassessed
  (moving it would strand the remaining events). Refusals are 409 with the
  reasons as finished UI copy.

Verified end to end against the local D1: dropped material, chose an existing
project from the picker, confirmed the material landed there and
`routing_source` was written as `user`; then accepted a suggestion and confirmed
the event, its asset and its transcript segment all moved and the suggestion row
was cleared. One bug surfaced only in that real run and is fixed: the picker was
handed the upload's busy state, which disabled every button and left the user
stuck in a dialog they could not answer. Source-text tests cannot catch that
class of defect.

## The citation-support judge is measured, and still cannot ship (sixth batch)

The four non-compensating gates in `lib/domain/judge-calibration.ts` were run
against Jev for the first time (`npm run judge:calibrate`, 127 samples, ~$0.13).
Accuracy 0.976 and expected calibration error 0.067 both clear their thresholds.
Sample size does not: 127 against a floor of 200. The worst-bucket gap of 0.900
is an artifact of a bucket holding one sample, where the observed rate can only
be 0 or 1, and the runner says so in its own output.

The shortfall is data, not the model. The local database holds zero human
verdict rows, so every sample came from the offline eval fixtures, which are
exhausted at 127. Seventy-three more real labels are needed, and they can only
come from people actually confirming content in the product. The judge stays
unwired, and the explainer page continues to mark it 未上线. Full record in
`docs/judge-calibration/2026-09-21.md`.
