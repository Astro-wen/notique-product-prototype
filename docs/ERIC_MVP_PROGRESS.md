# Notique MVP 给 Eric 的阶段说明

更新日期：2026 年 8 月 13 日

## 1. 一句话说明方案

Notique 把一次沟通先整理成一份带原文出处的 AI 初稿，再让人快速核对。只有人确认过的内容，才会进入长期项目记忆、时间线和会前报告。

AI 的任务是减少整理工作；人的任务是决定哪些内容可以成为正式事实。

## 2. 这套系统的基本原理

1. 用户上传逐字稿、录音、照片或 PDF。
2. 录音先变成带说话人和时间点的逐字稿。
3. 第一位 AI Agent 使用 Luna `xhigh`，尽量完整地盘点原子事实。
4. 第二位 AI Agent 使用 Luna `high`，检查漏项、重复、前后变化和证据；必要时才升级到 `xhigh` 再检查一次。
5. 程序核对原文出处，不允许模型自己编造 Evidence ID、引文或时间点。
6. 用户确认、修改、拒绝或补充。
7. 只有已经确认的记录进入正式结果。报告本身由规则生成，不再调用另一个 AI 把错误“写得更像真的”。

两个 Agent 共用同一个 API Key，不需要两套账号或两把密钥。

## 3. Eric 所说的“不靠 Verification”是什么意思

这句话不是要取消人工核对。Eric 真正想知道的是：在人工开始修正以前，AI 的第一版是否已经抓住了大部分重要内容，还是必须由人从头重做。

因此方案把两个问题分开记录：

1. **人工核对前：** AI 初稿本身有多好，漏了什么，错了什么。
2. **人工核对后：** 正式项目记忆是否可靠、可追溯。

Verification 仍然是安全门，但不能再被用来掩盖 AI 初稿的真实质量。

## 4. 现在能做

### 4.1 从材料到 AI 初稿

1. 可以上传自己的 Transcript、录音、照片和 PDF；也可以直接使用浏览器录音。
2. 录音会先生成带说话人和时间点的逐字稿，再进入事实识别。
3. 双 Agent 会分别完成“全量盘点”和“查漏纠错”，最终只把有 Evidence 的候选交给人。
4. AI 初稿按时间和业务主题整理，每个重点可以回到对应记录与证据。

### 4.2 人工核对与长期记忆

1. 用户可以确认、修改、拒绝，也可以补上 AI 漏掉的重要内容。
2. 如果一条新信息会取代旧决定、解决旧问题或形成矛盾，关系必须由人接受或拒绝。
3. Pending 和 Rejected 内容不能进入正式报告。
4. 后续沟通只继承已经确认的项目记忆，不继承 AI 尚未核对的猜测。

### 4.3 本轮完成的体验与速度修复

1. **返回位置可预测。** 页面地址会记录当前项目、沟通、栏目和记录。时间线打开证据后会返回时间线，审核列表打开记录后会返回原审核位置；刷新也能恢复当前页面。
2. **已确认记录是只读阅读模式。** 从报告打开已确认记录时，不会再混入无关的 Pending 连续审核队列。
3. **当前任务被直接唤醒。** 用户创建分析任务后，服务器以 `202 Accepted` 立即确认，并定向启动刚创建的 Run，不再让它排在全局旧任务后面。
4. **等待时间按真实阶段显示。** 首次排队、本轮重新排队、材料准备、Agent A `xhigh`、Agent B `high`、加强复核和写入结果分开计时。
5. **减少页面重复请求。** 一个 workflow snapshot 会一次返回当前项目的沟通、材料、Run、场景、待核对数量和唯一下一步，避免页面不断发出零散查询。
6. **Evidence 更容易读。** 证据合同默认提供目标句前两段和后两段；目标短语单独放大并精确高亮，有音频时可从目标位置附近播放。
7. **时间线真正表示变化。** Timeline 使用纵向时间节点表达新增、取代、解决、矛盾、再次确认和撤回，不再只是“事项概况”的另一种排版。
8. **偏好可以看历史。** Preference 会显示当前偏好、条件、决策人、首次出现、最近确认和历史变化。

### 4.4 新增：把“原始记录、易读版本和摘要”分开

Eric 在会议里提出，希望用户先看到一份容易读的内容，再点击重点判断“是不是这个意思”。方案现在把三层内容明确分开：

1. **原始逐字稿永远保留。** 说话人、原句、时间点和音频位置不被 AI 覆盖，正式 Evidence 仍只认这一层。
2. **易读逐字稿只改善阅读。** Luna `high` 可以补标点、分段、合并被切碎的短句，也可以隐藏明显没有语义的卡顿；但金额、日期、数量、否定、审批人、责任人、承诺和条件不能静默改变。
3. **AI 摘要帮助快速进入重点。** 另一条 Luna `high` 任务生成章节、决定、偏好、问题、风险和下一步。每个重点必须附一段真实原话和原始位置，否则会被程序拒绝。
4. **事实识别保持原来的质量边界。** Agent A 仍只读原始逐字稿；Agent B 可以参考易读稿，但正式 Claim 和 Evidence 仍要回到原始 Segment。
5. **长会议不会整份重来。** 易读稿按原始顺序分块，每块保存独立请求 ID、用量和结果。刷新或后台中断后会从未完成的块继续；最后仍要通过一次全局“无遗漏、无重复、顺序不变”检查。

这部分已经在本地完成代码、迁移、259 项自动化和桌面/390px 手机布局验收，但还没有发布到当前 Sites v17，也没有发起新的付费模型 Run。这里应写成“工程完成、待线上模型验收”，不能写成摘要或易读稿质量已经通过。

### 4.5 新增：项目回收站

1. 当前项目旁只有一个项目菜单，删除动作不会在不同页面重复出现。
2. “移到回收站”前会显示项目名称、沟通、材料和待核对数量；仍在转写或分析的项目不能删除。
3. 删除后项目从主列表消失并自动打开下一个项目；回收站可完整恢复材料、记忆、Evidence 和报告。
4. 永久删除必须输入完整项目名。方案先删除文件存储中的录音、照片、逐字稿和暂存结果，全部成功后才删除数据库记录；中途失败仍留在回收站重试。

本地已经实际走完“新建空项目 → 移到回收站 → 恢复 → 再次删除 → 输入完整名称永久删除”。正式站仍待发布后复验。

这轮已经发布到原来的公开测试站，当前版本为 Sites v17。桌面端已用现有的已确认记录完成只读验收：时间线、证据、页面返回、浏览器返回、报告栏目和刷新恢复都符合预期，浏览器控制台没有报错。手机布局已通过样式和自动化检查，但还没有在真实手机浏览器完成同样的人工验收。

## 5. 为什么曾经显示“排队 10 分 47 秒”

那次并不是 Luna `xhigh` 单独思考了十分钟。

拆开后可以看到：真正的两阶段模型处理大约是 **1 分 36 秒**，其余主要是后台任务没有及时被领取，以及重试后仍沿用第一次排队起点，导致页面把多段等待合并成一个很大的数字。

本轮的修复不是降低模型质量，而是：

1. 创建任务后直接唤醒当前 Run。
2. 15 秒还没有被领取时，重新唤醒同一个 Run，不创建第二次付费任务。
3. 定时任务继续作为最后兜底。
4. 重试单独计算“本轮排队”，同时保留首次等待历史。

目标是正常情况下 `queued → processing` 的 P95 小于 10 秒；如果后台即时唤醒失效，最后兜底小于 130 秒。Sites v17 尚未用新后台架构发起付费 Run，这个目标仍不能只凭代码和只读验收判定已经达到。

## 7. 第一次公开许可真实录音结果

方案已经实际跑完 AMI Meeting Corpus 的 `ES2002a`：一段约 21 分钟、四人参与的产品设计项目启动会议。8 条评分事实是在模型运行前写定的，因此这次结果没有为了好看而临时改答案。

### 7.1 先看最容易理解的结果

1. **录音转逐字稿：8/8。** 售价 25 欧元、成本上限 12.50 欧元、国际销售、电视功能范围未定、三位负责人的分工和会议范围，都能在派生 Transcript 中找到。这个 8/8 只代表八条关键事实被保留下来，不代表整场逐字稿的逐字错误率已经测完。
2. **AI 原始初稿：命中 6/8。** 模型最终提出 10 条候选，其中完整覆盖了预先写定的 8 条事实中的 6 条；遗漏的是“国际市场”和“是否只限电视功能”。重要事实 Recall 为 75%，低于 90% 目标；四条 Critical 只抓到两条，即 50%，没有通过 100% 硬门。
3. **安全门后的可审核初稿：只剩 6 条。** 10 条中有 4 条因为引用没有通过程序核对而被挡住，没有交给用户确认。被挡住的四条里包含“成本上限”和“市场负责人的任务”，因此用户真正看到的版本只覆盖 4/8，Critical 只剩 1/4。
4. **没有发现凭空编造的候选。** 人工回看 Transcript 后，原始 10 条都能找到事实依据；其中 4 条是 Ground Truth 之外、但会议里确实说过的内容。它们不能拿来弥补漏掉的预定事实，也不应被误写成四条错误。

### 7.2 Evidence 为什么仍然没有通过

程序成功保证了：进入审核的 6 段引用全部逐字来自 Transcript，引用和服务器 Segment 的时间一致，机械层面的准确率是 6/6。

但“逐字存在”还不等于“足以证明整条结论”：

1. 售价、项目范围、1,500 万欧元目标和下次会议时间有直接支持。
2. David 和 Craig 的两条记录最后只保留了他们自我介绍职位的原句，没有保留真正分配任务的后文；因此 Evidence 不足以单独证明完整的任务和截止时间。
3. 按运行前固定的“与人工定位相差小于 5 秒”规则，落库后与 Ground Truth 重合的四条里只有售价满足；其余使用了会议里另一次提及，或者使用了跨度太大的说话段。

因此这次不能写“Evidence 硬门通过”。程序挡住了四条不合格引用，这是好事；但它没有继续为其中两条已落库记录找到足够直接的替代证据。

这次 Run 之后，方案已补上一个保守修复：如果模型用 `...` 或 `…` 省略同一段连续原话，程序会按顺序寻找所有非空片段；只有整场材料中恰好存在一个连续答案时才接受。缺失、乱序、跨越不连续 Segment 或存在多个可能位置时仍然拒绝。这个修复预计能保住 Andrew 的任务、成本上限，以及 David、Craig 的直接分工证据；但历史 Run 不会被事后改分，必须用同一冻结样本新跑一次才能给出新成绩。售价口径和多设备方向使用了不连续证据，仍会被安全门正确挡住。

### 7.3 时间花在哪里

| 阶段 | 本次耗时 |
|---|---:|
| 录音排队 | 0.01 秒 |
| 录音转写 | 6 分 51.7 秒 |
| 事实识别排队 | 0.009 秒 |
| Agent A：识别事实 · `xhigh` | 1 分 28.4 秒 |
| Agent B：查漏纠错 · `high` | 30.3 秒 |
| 加强复核 · `xhigh` | 1 分 09.1 秒 |
| 从开始转写到初稿完成 | 9 分 59.6 秒 |

这次排队已经不是问题：两次排队都小于 0.02 秒。主要时间来自 21 分钟音频的转写，以及三次模型阶段本身。加强复核最后没有改善结果，系统保留了上一份较稳的版本并以警告完成；后续应优先减少无效升级和改善长音频转写体验，而不是把等待统称为 Luna 在“卡住”。

### 7.4 这次真正证明了什么

1. 公开许可的真实多人音频可以完整经过上传、转写、双 Agent、Evidence 核对和待审核初稿链路。
2. 关键数字、否定词、开放问题和人员分工都被 Transcript 保留下来。
3. 服务器 Evidence 安全门会诚实挡住不合格引用，不会为了凑十条而强行落库。
4. AI 的重要事实取舍仍未过关：原始初稿 Material Recall 75%，Critical Recall 50%；安全门后又降为 50% 和 25%。
5. 这是一场受控的产品设计会议，不是房地产客户通话，也只有一次沟通。它不能证明真实销售场景或跨沟通 Preference progression。

运行证据：Extraction Run `run_603f383e77264fafa9c773b1cda18149`。本次没有确认 Scenario 或任何 Claim，以上成绩全部是人工核对前的 AI 初稿成绩。

## 8. 需要再花时间看看

1. **复测 Evidence 选择。** 连续原话中的省略号引用已经修复；下一次应先确认成本上限和三位负责人的直接证据是否能保留，再处理售价口径、多设备方向这类真正不连续的引用。不能为了提高 Recall 放宽连续性和唯一性门槛。
2. **再修重要事实取舍。** “国际市场”和“是否只限电视功能”在 Transcript 中都很清楚，却没有进入最终十条；需要调整 inventory priority 和 verifier selection。
3. **减少无效加强复核。** 本次第三阶段多花 1 分 09 秒但没有改善输出，应让升级原因更具体，并在不改善时更快回到第二阶段结果。
4. **真人审核。** 还缺一名没有看过 Ground Truth 的用户完成整套核对，并确认是否能在两分钟左右完成。
5. **真实业务连续沟通。** 若能合法取得同一客户旅程的第二份材料，再测试 Preference 如何变化；不能用两段无关录音拼出一个假旅程。
6. **手机和线上运行。** 桌面只读链路已经在 Sites v17 通过。仍需在真实手机浏览器测试返回、刷新、Evidence、连续审核和 Timeline；新后台架构也还没有在 v17 发起新的付费 Run，不能把本次只读验收当成线上付费处理验收。

## 9. 当前不能证明

1. 不能宣称总准确率已经达到 95%；95% 是验收门，不是当前成绩。
2. 不能用人工修正后的正确报告证明 AI 初稿正确。
3. 不能用一段受控产品会议证明房地产、保险或真实销售场景已经成功。
4. 单个 AMI 会议不能证明跨多次客户沟通的 Preference progression。
5. 不能把公开测试站称为正式多用户 SaaS；当前测试者共用一个测试 Workspace 和模型额度。
6. 不能把本次关键事实转写 8/8 写成整场 Transcript 的逐字准确率；还没有计算完整 WER。
7. 不能说 PDF 已经可靠参与事实识别；没有可用的页面文本适配器时，系统会明确报错。
8. 不能说 Sites v17 已完成真实手机浏览器验收。
9. 不能把桌面只读验收写成新后台架构或付费处理已经在线通过，也不能据此判断 P95、模型质量或费用。

## 10. Eric 可以怎样亲自验收

1. 打开正式测试站，选择或建立一个项目。
2. 上传一份 Transcript 或小于 25 MB 的录音。
3. 材料准备好后，点击一次“开始分析”。
4. 先读 AI 初稿，并点击一个重点查看放大的原句和前后文。
5. 使用页面箭头返回，确认它回到原来的初稿或时间线位置。
6. 进入连续核对，对每条记录确认、修改或不采纳；有 Relation 时先处理关系。
7. 刷新页面，确认仍处于同一项目、沟通和记录。
8. 完成后查看 Timeline、Preference 和会前速览，确认只有已核对内容出现。
9. 最后记录：AI 漏了几条、改了几条、拒绝几条，审核花了多久。

验收的核心不是“页面看起来像 AI”，而是 AI 初稿是否真的节省工作，每条正式内容是否可以回到证据，以及前后变化是否容易看懂。
