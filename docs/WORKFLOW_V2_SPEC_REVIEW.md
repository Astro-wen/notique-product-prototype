## 第一轮：来源与现状

逐页读取并检查 ByteHi 前端技术方案的 17 页模板，沿用十章结构、模块说明字段、表格、目录代码块、流程图与时序图。重新阅读 Eric 在 2026-09-22 会议中 14–25 分钟及 36–50 分钟的产品讨论，并对照完整记录定位需求。

Eric 的核心要求为房仲重点正确性、使用顺畅、减少重复核对、出处追溯、纠正后更新结果、可交给团队实施和用授权真实材料测试。会议转写中不清楚的正确率数字没有转成验收承诺。MCP 来自会后沟通。

代码核对覆盖现有 Claim 与版本、证据、审核记录、行动完成关系、任务 outbox、接口响应和身份上下文。现有完成行动已经保存完成记录与关系，方案沿用这套账本扩展答案回流。

## 第二轮：产品出口与闭环

七个已识别断点在前端第十章逐项对应操作和通过条件。三条主路径为只读后离开、纠错后重开、行动到答案再到新沟通。

复核中补入的规则：

- 未决问题可以直接回答，使用 `QuestionAnswerRequest`，结果修正和撤回与行动结果共用机制。
- 完成行动与解决问题分别记录。没有拿到答案时允许行动已完成、问题仍打开。
- 修改并保存就是一次明确采纳，保留原文限定词和用户补充来源。
- 原文约定与加入行动使用不同决定，`next_action` 只能通过 `accept_action` 采纳。
- 用户处理部分内容即可退出，待批数量可以大于零。
- 一个问题可有多个有效答案，撤回最后一个有效答案后问题重新打开。

## 第三轮：接口与一致性

两份方案的接口表和数据类型表来自同一份定义，分别写入飞书后回读比较。

复核中补入的规则：

- `workflowRevision` 随文本、判断和有效关系变化递增，避免只靠文本版本漏掉关系变化。
- 写回执携带 `contextVersion`，后续查询通过 `minContextVersion` 保证至少读取到已保存版本。
- 幂等回执查询在权限校验之后、可变版本检查之前，网络重试返回同一次操作结果。
- 批次事务同时处理决定、依赖失效、outbox 与回执，旧租约和旧输入版本均受写回检查。
- 正式报告只纳入当前有效采纳信息，陈旧概要和失效出处有明确处理路径。
- 来源替换、移动、删除、恢复和永久清理同步处理引用、缓存、报告和 MCP。
- V1 与 V2 共用领域写入口，历史概要保留旧版标识，确定性迁移与模型重跑分开。
- 批阅同步处理的模型调用为零，自动概要重写单独计费。只读请求不会新建模型任务。
